# CLAUDE.md — model-harness

## What this is

**SapphireGuard.ModelHarness** is a .NET 10 agent framework that wraps LLMs with structured scaffolding. An *agent = model + harness* — the harness (loop, guides, sensors, budget) is what turns a raw model into a controllable agent.

## Build & run

```bash
dotnet build SapphireGuard.ModelHarness.slnx
dotnet run --project samples/HappyPath
```

Add an API key first (per-sample; samples fall back to `FakeModelClient` when absent):

```json
// samples/HappyPath/appsettings.local.json
{ "Anthropic": { "ApiKey": "sk-ant-..." } }
```

## Core patterns

### HarnessLoop
Turn-by-turn state machine: check budget → sensors (PreModelCall) → build context via guides → call model → sensors (PostModelCall) → dispatch tools → sensors (Pre/PostToolCall) → repeat.

Invariants:

- **Budget exhaustion is control flow, not an exception** — one final model call with tools disabled, then `PartialResult`.
- **Only `EndTurn`, `StopSequence` and `ToolUse` are normal endings — the check is an allowlist** (`CutShortReason`). Every other `StopReason`, including `Other` and any member added later, returns `PartialResult` with a `FailureReason` naming the cause and remedy. It runs after `PostModelCall` (content gates still apply), before tool dispatch (a cut-short call may carry partial arguments) and before `PreReturn`, and spends no extra model call. Adapters map a reason they do not recognise to `Other`, never `EndTurn`; `StopReason` members are only ever appended, because checkpoints persist it as an integer. → [ADR-004](docs/decisions/004-response-is-final-only-when-it-ended-normally.md)
- **Only genuine cancellation (`ct.IsCancellationRequested`) makes a run `Failed`/"cancelled"** — a collaborator's own timeout is a fault like any other, and its message becomes the `FailureReason`. Tools reach the same result by a different route: `ExecuteToolAsync` has no genuine-cancellation clause, so a tool's `OperationCanceledException` becomes a recoverable `IsError` result like any other throw (only the harness's own deadline gets the deadline message), and a genuinely cancelled run is caught by the next `ct.ThrowIfCancellationRequested()`. → [ADR-001](docs/decisions/001-collaborator-timeout-is-not-a-cancelled-run.md)
- **Wall-clock accrues across resumes** — `Budget.MaxWallClock` is measured from `AgentState.RunStartedAt` (the trajectory's first user message), not a per-`RunAsync` capture, so a HITL suspend, checkpoint reload, or new chat turn keeps accumulating instead of restarting. `TurnScopedBudgetEnforcer` anchors to the *latest* user message instead, matching its per-turn allowance.
- **`IBudgetEnforcer.Check(state, lookahead)` derives its anchor from the trajectory** — no `startedAt` parameter. The optional `lookahead` lets the rate-limit backoff guard ask the enforcer whether sleeping would exceed the cap rather than doing its own wall-clock math.
- **`Checkpoint.RunId` comes from `AgentState.RunId`** (the first user message's step id), never minted per `RunAsync`, so every checkpoint for a task shares one run id across a suspend/resume.
- **The turn index is derived, never counted** — `Trajectory.OfType<ModelCallStep>().Count()`, recomputed each iteration, and `DefaultGuideRunner` derives the same value the same way. A counter drifts in exactly two places: a rate-limit `continue` appends no `ModelCallStep` (burning an index no model call used), and a resume would restart from zero while the guide's derived index kept going. Deriving also subsumes resume seeding for free.
- **`Budget.MaxToolCallDuration`** (optional, null = off) wraps each dispatch in a `TimeProvider`-based linked `CancelAfter`; a timeout becomes a recoverable `IsError` result, not a run failure. Cooperative — it bounds tools that honour their token.
- **Model calls get no second harness deadline** — the provider SDKs apply their own request timeout, tunable via each adapter's `ConfigureClient` hook. A second one would duplicate it and re-raise the ADR-001 ambiguity.

### Guide pattern
Guides run **sequentially** before each model call, each contributing to a shared `ContextDraft`. Pipeline order is explicit and fixed: `HarnessInstructionsGuide` → `ReActGuide` → `MemoryGuide` → `ToolSelectorGuide` → `ToolCatalogueGuide` → `SkillsGuide` → `PinnedContextGuide` → [custom guides] → `HeadEvictionTrajectoryGuide`. `HeadEvictionTrajectoryGuide` is always last so it can measure all prior contributions and compute an accurate token budget. `ToolSelectorGuide` must precede `ToolCatalogueGuide` — the catalogue renders whatever tools the selector has approved. `ReActGuide` only appends Thought/Action/Observation framing to the system prompt, so its slot among the prompt-building guides is not load-bearing. Add custom guides with `builder.WithGuide<T>()`; they slot in before `HeadEvictionTrajectoryGuide`. After each guide (and the trajectory guide) runs, `DefaultGuideRunner` emits a `GuideContribution` via `ITracer.LogGuideContribution` — the structural delta that guide made to the draft (tools added/removed by name, memory snippets, system sections, trajectory messages, system-prompt char delta) — computed as a generic before/after diff so it works for every guide, including third-party ones, without the guide knowing about tracing. This surfaces the shaping decisions that never reach the final prompt (which tools a selector dropped, whether memory retrieval returned anything). `LogGuideContribution` is a default-interface no-op for back-compat; `ConsoleTracer`, `OpenTelemetryTracer`, and `CompositeTracer` implement it. A **supporting** guide that throws is caught by `DefaultGuideRunner`, skipped (its optional contribution lost for that turn), and logged via `ITracer.LogGuideError` (another default-interface no-op) — so a memory store timing out or a skill store failing to read degrades the turn's context rather than crashing the run. That includes the guide's *own* `OperationCanceledException` (a store's HTTP timeout raises `TaskCanceledException` with the harness token untouched): only genuine cancellation (`ct.IsCancellationRequested`) propagates, matching `DefaultSensorRunner`. The mandatory trajectory guide is deliberately **not** wrapped: a turn with no rendered trajectory is worse than surfacing the failure. Model and tool calls are bracketed as **scopes**, not post-hoc events: the loop calls `ITracer.BeginModelCall`/`BeginToolCall`, gets an `IModelCallScope`/`IToolCallScope`, `Complete(response/result)`s it, then disposes it (`using`) — a scope disposed *without* `Complete` (the call threw) is recorded as a failed span. When a **model** call throws (after the SDK's own retries exhaust), the loop first calls `IModelCallScope.Fail(exception)` (a default-interface no-op) so the `chat` span carries the exception detail — `OpenTelemetryTracer` emits the standard OTel `exception` event (`exception.type`/`message`/`stacktrace`) + Error status instead of a bare "did not complete", `ConsoleTracer` emits a `model_call` line with the error; genuine cancellation (the harness token) is excluded — expected control flow, not a call failure — but the client's *own* timeout is not: it is an `OperationCanceledException` only by accident of how `HttpClient` reports it, so it gets `Fail` like any other fault. Tool failures already carry detail — `ExecuteToolAsync` turns a throw into an `IsError` `ToolResult` that `Complete`s the span — so `Fail` is model-call-only. This lets `OpenTelemetryTracer` emit a nested OTel GenAI span tree (`invoke_agent` root → `chat {model}` / `execute_tool {name}` children carrying `gen_ai.*` attributes, plus the `gen_ai.client.token.usage` + `gen_ai.client.operation.duration` metrics) instead of flat events on one `agent.task` span; `ConsoleTracer` emits its `model_call`/`tool_call` JSON line on `Complete`; `CompositeTracer` fans one scope out to child scopes. Sensor and guide contributions stay event-shaped (`LogSensorResult`, `LogGuideContribution`, and `LogCompaction` — the last emitted by `DefaultGuideRunner` when the trajectory guide compacts, carrying a `CompactionTrace` of steps evicted / tokens reclaimed / folded / spend; `OpenTelemetryTracer` renders it as a `compact_context` event plus a `harness.compaction.tokens_reclaimed` histogram). Three more per-turn hooks close the loop's remaining blind spots — `LogRateLimit` (a rate-limit backoff wait), `LogCheckpoint` (each checkpoint save + its duration), and `LogBudgetSnapshot` (cumulative turns/tokens/cost/wall-clock vs the run's `Budget`, so burn-down is visible before the terminal `PartialResult`) — all default-interface no-ops emitted by `HarnessLoop`; `OpenTelemetryTracer` renders them as `harness.rate_limit`/`harness.checkpoint`/`harness.budget` events (plus `harness.ratelimit.wait` + `harness.checkpoint.duration` histograms), `ConsoleTracer` as `rate_limit`/`checkpoint`/`budget` JSON lines. `LogSensorResult` fires for **every** evaluation (pass, intervention, or error), not only interventions — `OpenTelemetryTracer` counts them all on a `harness.sensor.evaluations` counter (tagged by verdict) but only span-events the interventions/errors, so the root span doesn't bloat on passes. Every event and span carries a zero-based `turn` index so a backend can group all of a turn's work: the loop **derives** it afresh each iteration from the count of `ModelCallStep`s in the trajectory (not from an incrementing counter) and threads it into `BeginModelCall`/`BeginToolCall`/`LogSensorResult`, and `DefaultGuideRunner` derives the same index the same way (the current turn's model call isn't appended until after guides run, so the count *is* the turn index). Deriving rather than counting is what keeps the two aligned in the two places a counter drifts. **Across a resume**: a HITL suspend/resume, checkpoint reload, or new chat turn re-enters `RunAsync`, and a from-zero counter would restart the loop-emitted turn numbering (model/tool/sensor spans, `LogCheckpoint`/`LogBudgetSnapshot`, `Checkpoint.TurnNumber`) while the guide-derived index — read from the restored trajectory — kept counting. **Across a rate-limit backoff**: that iteration `continue`s without appending a `ModelCallStep`, so an incremented counter burned an index no model call ever used and ran +1 ahead of the guide for the rest of the run. Deriving subsumes the resume seeding for free — a restored trajectory carries its own count. `ModelResponse` carries `Model`/`Provider` (populated by every adapter) to source `gen_ai.request.model`/`gen_ai.provider.name`, plus `CachedInputTokens`/`CacheWriteTokens` — the prompt-cache breakdown of `Usage.InputTokens` — which `OpenTelemetryTracer` splits into disjoint `cache_read`/`cache_creation` token types on `gen_ai.client.token.usage` (the `input` bucket becomes the uncached remainder) plus `gen_ai.usage.cache_read_input_tokens`/`cache_creation_input_tokens` span attributes, so cache hit-rate is observable; `ConsoleTracer` adds `cacheRead`/`cacheWrite` to its `model_call` line. `ModelResponse` also carries `InputTokensTowardRateLimit`, which is **not** the billed input: Anthropic excludes cache reads from ITPM, so `ClaudeModelClient` reports uncached input + cache writes and `TokensPerMinuteRateLimiter` counts that instead of the folded prompt — otherwise a well-cached agent throttles several times too early, and worse the better its cache performed. Adapters whose provider rules are not established leave it null and get the full prompt counted, which throttles early rather than late. The span-aware `ITracer` shape (`BeginModelCall`/`BeginToolCall` replacing `LogModelCall`/`LogToolCall`) is a breaking change for external tracer implementations. For **local** observation with no backend at all, `LiveDashboardTracer` implements the same hooks as a zero-dependency in-process feed: it projects each event to a `DashboardEvent` pushed to a bounded ring buffer (so a browser connecting mid-run replays the history) plus live subscribers, surfacing metadata + short summaries (tokens, cost, tool names, sensor verdicts, budget burn-down) — not full message bodies, which stay `OpenTelemetryTracer`'s job. `DashboardEvent.Turn` is nullable — run-level events (`run`, `done`) carry a null turn so a UI renders them outside any per-turn group. Compose it alongside OTel via `WithLiveDashboardTracer()`. The ASP.NET Core hosting ships as a separate package, `SapphireGuard.ModelHarness.Dashboard` (project `Infrastructure.Dashboard`): `app.MapHarnessDashboard(prefix = "/dashboard", onRun?)` serves an embedded page + assets + an SSE feed (no OTLP, collector, or Docker), grouping the stream by run and by turn with per-event drill-in, a keyword filter over the runs list, and the run's final result. The page/assets are embedded resources with a `<base href>` injected so the dashboard works under any `prefix`; it is a read-only monitor unless the host passes an `onRun` callback (which reveals a demo run bar and maps `POST {prefix}/run`). The run/turn aggregation lives in the browser over the event stream, so the framework tracer stays a transport-neutral feed and only the `Dashboard` package takes a web dependency. `samples/LiveDashboard` wires `MapHarnessDashboard("/", onRun: …)` — that sample is the end-to-end reference. `LiveDashboardTracer(enableSensitiveData: true)` includes each model response's text in its `model` event detail (off by default, matching `OpenTelemetryTracer`), which the sample renders as the result panel — the final answer is the last model response's text.

`MemoryGuide` retrieves against the **latest** `UserMessageStep` (falling back to `TaskText` when the trajectory has none), not the frozen `TaskText`. The store does relevance ranking, so the query must describe what the agent is working on *now* — in multi-turn chat that's the current question, not the opener. This is unconditional, not a chat seam: a single-task run only ever has one `UserMessageStep` and its content *is* `TaskText` (nothing else appends one during an autonomous run), so task-mode behaviour is unchanged and no mode flag is needed.

Compaction is the one place a guide's output flows **back** to `AgentState`, through a single loop-owned channel: `HeadEvictionTrajectoryGuide` calls `ICompactionStrategy.CompactAsync(CompactionRequest, ct)` with the **typed** newly-evicted steps + `PriorSummary` and puts the `CompactionResult` on `ContextDraft.Compaction`; `DefaultContextBuilder` surfaces it on `ContextBuildResult`; `HarnessLoop.CallModelAsync` commits `RollingSummary` and accumulates `CompactionUsage`/`CompactionCost`. `UpdatedSummary = null` is a stateless *view* (`NullCompactionStrategy` default); non-null is an incremental *fold* (`AiCompactionStrategy`), with `RollingSummary.FoldedStepCount` as the watermark the guide skips. → [ADR-002](docs/decisions/002-incremental-fold-compaction.md)

Four invariants must hold, and breaking any one of them is silent:

1. **System-role trajectory messages fold into the single system message.** The rolling summary and the `[ORIGINAL GOAL]` anchor are emitted as `MessageRole.System` trajectory messages, and `DefaultContextBuilder` folds them in — each adapter forwards only the *first* System message and drops the rest, so anything left inline would never reach the model.
2. **Everything rendered into the window is charged before trimming** — the anchor by its rendered length (`OriginalGoal(...)` is one definition shared by the charge and the render, so the two cannot diverge), the new summary via the prior summary's size as a stand-in. Omitting them overshoots `WindowTokens` on every compacted turn. Invariants 1 and 2 are a pair — see ADR-002 for why.
3. **Eviction never removes the most recent group** — `ComputeTrimCount` is capped at `liveGroups.Count - 1`, with a fallback that renders the last group even when the watermark covers everything. A fully-evicted turn would produce an empty `messages` array, which Anthropic and Azure reject with a 400.
4. **The fold fails open, never silently.** A throwing strategy falls back to an omission note (its own timeout included — only genuine cancellation propagates, per ADR-001), and the reason always travels on `CompactionResult.Error` → `CompactionTrace.Error` into every tracer. A pass carrying an `Error` never reports `Folded`. A result that persists nothing describes only the newly evicted slice, so it renders *behind* any prior summary, never in place of it.

The eviction **trigger** is `CompactionOptions.WindowTokens` (one context window), deliberately separate from `Budget.MaxTotalTokens` (the cumulative run cap). Both opt-in methods require `CompactionOptions`, so a strategy is never wired without its trigger; the `WindowTokens = 100_000` default keeps compaction dormant unless a run genuinely overflows.

**Pinned reference content** (`ToolResult.Pins` → `AgentState.Pins` → `PinnedContextGuide`) protects foundational content from eviction. Head-eviction drops the *oldest* trajectory steps first, but the oldest are often the most load-bearing — a loaded procedure or output contract. An agent that loads its procedure via `skill_view` at turn 0 and enforces its output format would lose the contract to eviction, then fail to reproduce the format while an output sensor rejects it to the intervention cap (the sensor↔eviction trap: eviction drops the contract not knowing a sensor enforces it; the sensor rejects not knowing the contract was evicted). The fix: a tool returns `PinnedNote { Label, Content }` on `ToolResult.Pins`; the loop commits them to `AgentState.Pins` (replace-by-label) at execution time; `PinnedContextGuide` renders them as non-evictable **system sections** every turn — the same persistent region as the `[ORIGINAL GOAL]` pin and the tool catalogue, never touched by eviction/compaction. `SkillViewTool` uses it: it returns a short ack and pins the loaded skill body, so progressive disclosure (load on demand) is preserved *and* the loaded content survives compaction. This is the Letta/MemGPT core-memory-block pattern (labelled, in-context, persistent), written-on-load rather than agent-editable. `Pins` is checkpointed, so resume keeps loaded procedures. Pinned sections count toward the eviction window budget (they're real context), so a large pin correctly shrinks the room for episodic history.

### Sensor pattern
Sensors run **in parallel** at five hookpoints (`PreModelCall`, `PostModelCall`, `PreToolCall`, `PostToolCall`, `PreReturn`). A `SensorResult.Intervene(reason)` appends a `SensorInterventionStep` to the trajectory, which `HeadEvictionTrajectoryGuide` renders as a `[HARNESS OBSERVATION — ...]` assistant-role message on the next turn. The assistant role is deliberate — the model "owns" the correction (self-consistency), the same lever prefill pulls. But when such a note is the **final** turn before a model call (every intervention hookpoint can produce this — `PreModelCall` does it on the same turn), the request would end on an assistant turn, which newer Claude models reject with a 400 (the retired prefill behaviour). So `HeadEvictionTrajectoryGuide` appends a trailing **user** turn ("Proceed, fully complying with the harness observation above.") whenever the last live step is a `SensorInterventionStep`: the note keeps its self-consistency framing, a user turn carries the API-required final role, and the external directive stacks on the self-commitment. `HarnessInstructionsGuide` primes the model in the system prompt to treat these notes as directives — feedforward and feedback working together. A sensor that **throws** fails open: `DefaultSensorRunner` catches it and returns `SensorResult.Failed(reason)` (flagged `IsError`, *not* an intervention), so one misbehaving sensor can't fault the parallel `Task.WhenAll` batch or take the run down, and the model keeps its turn. That includes a sensor's *own* `OperationCanceledException` — an AI sensor whose HTTP call times out raises `TaskCanceledException` with the harness token untouched — so only genuine cancellation (`ct.IsCancellationRequested`) propagates. The loop-detection sensors (`StuckDetector`, `AlternatingToolLoopSensor`, `MonologueLoopSensor`, `ToolErrorLoopSensor`) all stop their backward scan at the latest `UserMessageStep`: a new user turn is a fresh intent, so "N in a row" means within the current turn, never across the conversation. The failure is logged as an error via `LogSensorResult` (`OpenTelemetryTracer` tags the event `error.type=sensor_error`, carries the error reason (the runner's exception summary, or a sensor's own `Failed` reason) as `exception.message` — ungated, unlike an intervention reason, so a failing sensor is diagnosable without content capture — and does not count it as an intervention) rather than silently swallowed. For that reason a sensor should **not** catch its own failure and return `Pass`: the run behaves the same, but the fault hides behind a clean result. `CriticSensor` lets a failed model call propagate to the runner, and reports a verdict it cannot parse as `SensorResult.Failed(...) with { Usage, Cost }` — non-blocking and still charged, but an error rather than a pass. A sensor that must fail **closed** (a hard security gate) should catch its own exception and return `Intervene` instead — `TaintTrackingSensor` does exactly this at `PreToolCall`, because the fail-open default would let a privileged action through while tainted content sits in context, which is the one outcome it exists to prevent. Its catch uses the same two-clause shape as the runner, inverted: only genuine cancellation propagates (which ends the run before the tool is dispatched), and everything else — a custom `ITrustPolicy`'s own `OperationCanceledException` included — returns `Intervene`. A fail-closed catch written as `when (ex is not OperationCanceledException)` leaks exactly that case to the runner, which fails it open.

AI-powered sensors that call a model internally should return `SensorResult.PassWithUsage(usage, cost)` or `SensorResult.InterveneWithUsage(reason, usage, cost)` so the harness can accumulate the spend on `AgentState.SensorUsage` / `AgentState.SensorCost`. `DefaultBudgetEnforcer` includes these totals in its `MaxCost` and `MaxTotalTokens` checks.

Sensors may block actions but must never take turns away from the model — the model always gets the next call so it can self-correct. The loop decides what each intervention means per hookpoint:
- **PreModelCall**: **annotates** — injects the note into the trajectory then proceeds with the model call on the same turn; use for conditional pre-reasoning guidance (e.g. goal-drift warnings, error-streak alerts)
- **PostModelCall**: **rejects** — response is suppressed from trajectory so the model cannot re-see flagged content (e.g. PII); model gets a fresh turn to produce a clean response
- **PreReturn**: **challenges** — answer is not accepted; model gets a fresh turn with its prior answer visible so it can self-correct
- **PreToolCall**: **blocks** — tool is never dispatched; a `ToolCallStep` with `IsError = true` is recorded so the model sees a clean error and can replan
- **PostToolCall**: **flags** — advisory only; the tool has already run and its result is in the trajectory; intervention annotates it but cannot prevent the model from reasoning on it

### Structured output
`WithStructuredOutput<T>()` constrains the run's **final answer** to a type. No port, no loop change, no tool: one guide plus one sensor over a shared `StructuredOutputContract<T>` (schema + `JsonSerializerOptions` + `TryBind`), so the thing that states the contract, the thing that enforces it, and the caller that reads it cannot drift. → [ADR-003](docs/decisions/003-structured-output-as-a-prereturn-validator.md)

Invariants:

- **`StructuredOutputGuide<T>` states the schema as a `ContextDraft.SystemSections` entry, never a trajectory message.** System sections are rebuilt every turn and `HeadEvictionTrajectoryGuide` trims only the *trajectory*, so the contract is unreachable by eviction **by construction**. It needs no pin: pins bridge *trajectory-borne* content (a `skill_view` result) into the persistent region, and a guide's contribution is already there. Pins are for content the model discovered; guides are for content you declared.
- **`StructuredOutputSensor<T>` binds at `PreReturn`** — the one hookpoint reached only on a turn with no tool calls, so it is the final turn known with certainty. The schema is stated every turn as a system section, but generation is never constrained to it, so intermediate reasoning and tool-calling turns stay free.
- **A non-binding answer is repaired, not thrown** — `InterveneWithToolSuppression`, the binder's own error (naming the missing/malformed member) goes back as a `SensorInterventionStep`, and the loop's existing intervention cap bounds it to `PartialResult`.
- **`RespectRequiredConstructorParameters = true` is load-bearing** (with `RespectNullableAnnotations`) — without it `{}` binds to a default object and the validator is a rubber stamp. A unit test guards it; do not remove that test.
- **`TryBind` is lenient about transport, strict about shape** — strips code fences, extracts balanced JSON from surrounding prose trying each candidate until one deserializes, and inherits `JsonSerializerOptions.Web`.
- **A cut-short response never reaches `PreReturn`** — see the HarnessLoop invariants.

`[Description]` on the type and its members flows into the schema as `description` keywords. Non-object roots (`List<int>`, an enum) need no wrapper — the text channel carries any JSON value, unlike a tool-input schema. Sample: `samples/StructuredOutput`.

### State
`AgentState` is an immutable record. Every turn produces a new state via `with`-expressions. The trajectory (`IReadOnlyList<Step>`) is the append-only log of `UserMessageStep`, `ModelCallStep`, `ToolCallStep`, and `SensorInterventionStep`.

`AgentState.TotalSpend()` returns the run's cumulative `(Turns, Usage, Cost)` — model calls **plus** delegated `ToolResult.Cost`/`Usage`, `SensorUsage`/`SensorCost`, and `CompactionUsage`/`CompactionCost`. It is the single accounting behind `BudgetSnapshot.From` (and through it `DefaultBudgetEnforcer`) and `AgentTool`'s roll-up of a sub-agent's spend to its parent, so enforcement, telemetry, and delegated cost cannot drift apart. Walking `ModelCallStep` alone under-reports by exactly the three non-model sources, which is what made `AgentTool` charge parents low. Nesting sums correctly rather than double-counting: a delegated result already carries the sub-agent's *total*, and the grandchild's model calls live in the grandchild's trajectory. `TurnScopedBudgetEnforcer` deliberately keeps its own walk — its window resets at each `UserMessageStep`, so it cannot use a whole-run total.

## Key ports

Defaults differ by entry point: `AddModelHarness` (bare, `Framework`) wires core + no-op defaults; `AddStandardModelHarness` (`Infrastructure`) calls `AddModelHarness` then overrides a few seams and adds the default tools/sensors. **Neither registers a model client — the caller always supplies one** via `.WithModel(...)` / `.WithResilientModel(...)`. Port defaults use `TryAdd` (a matching `.WithX(...)` replaces them); tools, sensors, and guides are additive.

`AddChatHarness` (`Framework`) is a third entry point for multi-turn chat — a thin sibling of `AddStandardModelHarness`, not a fork. It calls `AddModelHarness` then swaps two seams: `TurnScopedBudgetEnforcer` (counts turns/cost/tokens since the last `UserMessageStep`, so each user turn gets a fresh allowance instead of the whole conversation exhausting one budget) and `HeadEvictionTrajectoryGuide(pinOriginalGoal: false)` (drops the `[ORIGINAL GOAL]` pin, since chat's live goal is the latest user turn). No task-completion sensors are wired. Same `HarnessLoop`, `AgentState`, and `Agent`; continue a conversation with `AgentState.WithUserMessage`. Sample: `samples/Conversation`. (Multi-turn memory retrieval needs no chat seam — `MemoryGuide` already queries the latest user turn unconditionally; see the Guide pattern above.)

`AddStandardChatHarness` (`Infrastructure`) is the opinionated sibling — it calls `AddChatHarness` then adds chat-appropriate standard defaults: `InMemoryToolRegistry`, `GetDateTimeTool`, OpenTelemetry tracing, and the `PromptInjectionSensor` + `StuckDetector` security/loop sensors. It deliberately omits the task-completion `ProgressCheckSensor`. `PromptInjectionSensor` scans both inbound tool results (PostToolCall) and the latest user message (PreModelCall) — the latter checks the current chat turn, not just the opener. Tool results include any `ToolResult.Pins` (pinned content lands in the non-evictable system region, so an injection there is *more* dangerous, not less), except for a small `TrustedTools` allowlist — `ask_human` (the pending result echoes the model's own question, which quotes injection text whenever the agent is triaging suspicious content) and `skill_view` (a stored procedure is instruction by nature — "never call X before Y" — so the patterns match legitimate guidance routinely). The exemption matters because PostToolCall is *advisory* and fires after the result is already committed: it cannot block anything, so a false positive only tells the model to distrust content it legitimately loaded. Both entries assume that source is operator-authored; a deployment where untrusted parties can write skills (agent learning) or answer `ask_human` (a relayed channel) needs a control at the write/ingress boundary instead — a regex over instruction-shaped text is the wrong instrument there. Sample: `samples/ChatSubAgent`.

The guide pipeline, `DefaultGuideRunner`, `DefaultSensorRunner`, `DefaultContextBuilder`, and `HeadEvictionTrajectoryGuide` are wired identically by both.

`TimeProvider` is registered as a singleton (`TimeProvider.System`) so every DI-resolved time-dependent component — `Agent`, `HarnessLoop`, the budget enforcers, the rate limiters, `ConsoleTracer`, `FileSkillStore` — reads one injectable clock; override it with standard DI (`services.Replace(...)`) rather than a dedicated builder method. Those components accept the clock by constructor injection (an optional `TimeProvider? = null` falling back to `TimeProvider.System`, except `Agent` which requires it), so direct construction still works without a container. `AgentState` is deliberately the exception: it stays a pure value type, so `NewTask` / `WithUserMessage` take a `DateTimeOffset timestamp` supplied by the caller (`Agent` passes `timeProvider.GetUtcNow()`) rather than depending on a clock at all.

## DI conventions

- DI registration files are named `DependencyInjection.cs`, class `DependencyInjection`, at the **project root** (not in a subfolder).
- Two-method pattern per abstraction: `AddXxx<T>()` (public, explicit override via `Replace`) and `AddXxxDefault()` (private, `TryAdd` — called only by `AddModelHarness`).
- Guides are a collection — `AddXxxGuideDefault()` uses `AddGuide<T>()` internally; opt-out by not calling the default.
- `AddModelHarness(systemPrompt)` is the single public aggregate entry point.

## Coding conventions

- SOLID principles and Clean / Onion Architecture with ports and adapters throughout.
- Primary constructors preferred.
- Interfaces over concrete implementations.
- Small, focused changes — build after each set of changes.
- Remove unused `using` statements in every file touched.
- No comments unless the WHY is non-obvious. XML doc comments belong on the public API surface only (this ships as a NuGet library, so consumers get IntelliSense) — keep them concise. Do not put XML docs on internal/private members; use a plain `//` comment there only where the WHY is non-obvious.
- No unnecessary abstractions — don't design for hypothetical future requirements.

## Workflow

- **Commit and push after every changeset** — do not wait to be asked.
- Before designing a non-trivial solution, ask clarifying questions to improve the spec.
- When using external SDKs or APIs, fetch up-to-date docs rather than relying on training data.
- **After any change, re-check the docs for staleness and fix them in the same changeset** — `README.md`, `CLAUDE.md`, and `docs/*.md` (PRIMER, EXTENDING, ROADMAP). If a change renames a symbol, removes a project, alters a default, or adds/removes a feature, update every doc that referenced it so the docs never drift from the code.
- **Record every breaking change in `CHANGELOG.md`, with a migration guide** (before/after code for anyone who has to change theirs). A breaking change is anything that can stop a consumer compiling *or* silently change runtime behaviour they depend on — this explicitly includes the extension-point interfaces (`IBudgetEnforcer`, `ITracer`, `ISensor`, `IGuide`, `IModelClient`, …), which are public API even though most consumers implement only a few. Note behavioural changes even when the signature is unchanged.
- **Releases are annotated `vX.Y.Z` tags** (MinVer — the tag *is* the version). Pushing one makes CI publish the eight packages to nuget.org **and** create the GitHub Release from the tag's annotation message, so write that message as the release notes. A published NuGet version can never be deleted or reused — confirm the number before tagging, and bump **major** for anything in the breaking list above.
